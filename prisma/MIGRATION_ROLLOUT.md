# Migration rollout — one-time baseline reconciliation

We switched the deploy from `prisma db push` to `prisma migrate deploy` (see the `start` script in
`package.json`). We also squashed the old, drifted migration history into a single `0_init` baseline
and added one hardening migration (`20260727000000_orgid_notnull_drop_dead_cols`).

## ⚠️ Read this first

Every database that was previously kept up to date with `db push` (local dev, v2 staging, and one
day production) already contains all the tables — but its migration ledger still lists the **14 old
migrations**, none of which match the new `0_init`. If such a database boots the new code as-is,
`migrate deploy` will treat `0_init` as unapplied and try to **`CREATE TABLE` everything that already
exists**, which fails and crash-loops the container.

So each existing database needs a **one-time reconciliation** (below) **before** it runs the new
`start`. This is not needed ever again, and it is not needed for brand-new databases (a fresh tenant
DB just runs `0_init` then the hardening migration cleanly).

Local dev (hayabusa) has already been reconciled and verified. This document is for **v2 staging**
first, then **production** when v2 is promoted.

## What the hardening migration does (so there are no surprises)

- Backfills any legacy `NULL` `orgId`: child rows inherit their parent's org; the three per-org
  aggregate/config tables under a unique constraint (`InventoryValueSnapshot`, `Settings`,
  `DismissedNotification`) have their stale NULL rows **deleted** (they are regenerated by the app);
  everything else goes to the founding (oldest) organization.
- Locks `orgId` `NOT NULL` at the database level on all 20 tenant tables.
- Drops the 4 dead `LotLine` columns: `teaCostPerUnit`, `otherCostPerUnit`, `teabagCostPerUnit`,
  `pouchCostPerUnit` (nothing reads or writes them).

It runs inside a transaction: if anything fails it rolls back and changes nothing.

## The reconciliation, per database

Run these against the target database (set `DATABASE_URL` to it). **Do production only at promotion
time, after a fresh backup, and never against the live `ops.herbl.co` DB by accident.**

**0. Back up the database first** (Railway → the Postgres service → create a backup/snapshot).

**1. Sanity-check you're pointed at the right DB** and see what the hardening migration will touch:

```bash
# Should print the tables with a couple of legacy NULLs (small numbers). If a business-entity table
# (Product/Supplier/Facility/MaterialType/PurchaseOrder) shows NULLs, stop and investigate before
# proceeding — those get assigned to the founding org and must not collide.
psql "$DATABASE_URL" -c "SELECT 'InventoryValueSnapshot' t, count(*) FILTER (WHERE \"orgId\" IS NULL) nulls FROM \"InventoryValueSnapshot\" UNION ALL SELECT 'Settings', count(*) FILTER (WHERE \"orgId\" IS NULL) FROM \"Settings\" UNION ALL SELECT 'PurchaseOrderLine', count(*) FILTER (WHERE \"orgId\" IS NULL) FROM \"PurchaseOrderLine\";"
```

**2. Clear the stale migration ledger and baseline the current schema as already-applied:**

```bash
psql "$DATABASE_URL" -c 'DELETE FROM "_prisma_migrations";'
npx prisma migrate resolve --applied 0_init
```

**3. Apply the hardening migration and confirm:**

```bash
npx prisma migrate deploy      # applies 20260727000000_orgid_notnull_drop_dead_cols
npx prisma migrate status      # → "Database schema is up to date!"
```

**4. (Production only) Confirm the cost anchors are unchanged** — production COG **269,846.21**, raw
**29,976.49** — via the dashboard, before announcing done.

After this, deploying the new code is safe: the container's `start` runs `migrate deploy`, sees both
migrations already applied, and boots normally.

## If `migrate deploy` fails

It rolled back — the DB is unchanged. The most likely cause is a unique-constraint collision while
assigning a legacy NULL `orgId` on a business-entity table (a genuine duplicate in the data). Read
the error's table/constraint, inspect those rows, and decide (merge, delete the duplicate, or extend
the migration's backfill) before retrying. To retry after a failure:
`npx prisma migrate resolve --rolled-back 20260727000000_orgid_notnull_drop_dead_cols`, then
`npx prisma migrate deploy` again.

## Note for whoever writes the NEXT migration

`orgId` is intentionally `String?` in `schema.prisma` but `NOT NULL` in the database (see the header
comment in `schema.prisma`). `prisma migrate diff` / `migrate dev` will therefore emit spurious
`ALTER COLUMN "orgId" DROP NOT NULL` lines — **delete those hunks** from any generated migration.
